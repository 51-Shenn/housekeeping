The rules

A room can only move one way

Every legal move lives in a single switch — HousekeepingControl.canTransition(). The method right below it, getValidNextStatuses(), returns the same table as an array, with the comment “Derived from canTransition so the two can never drift apart.” The menu you see on screen is built from that array, so the UI physically cannot offer an illegal move.

Current statusLegal targetsWhat it means on the floor
OccupiedDirtyGuest left; also set automatically on check-out
DirtyCleaning In ProgressCleaner has started — the only move available
Cleaning In ProgressInspected DirtySend for inspection, or restart the clean

ReservednonePrints “No valid status transitions available”
If it comes up

A Reserved room falls into the default: branch of canTransition() and returns false. That is deliberate — a room held for a confirmed booking is the front desk’s to release, not housekeeping’s.

Inside the DAO

One log, one stack per room

The private TaskStore class inside JsonHousekeepingTaskDAO keeps two structures, because the module has two different access patterns: an audit trail that must never lose a record, and an undo that only ever touches the newest change for one room.

The interesting part

Three guards stand between you and a bad undo

All three live in HousekeepingControl.undoLastUpdate(), and hasUndoHistory() runs the same checks — which is why the Undo? column already tells the truth before you press anything.

1

The room exists

Cheap, but it keeps a null out of the next two checks.

2

latest.getNewStatus().equals(room.getStatus())

The top of the stack must still match reality. If another module moved the room since that task was recorded, the undo is stale and is refused rather than stomping on newer state.

3

previousStatus is not “Occupied”

You cannot undo a check-out, because restoring the room to Occupied would contradict the booking record that says the guest has already left.

And one special restore rule

Undoing a check-in does not put the room back to Available:

String restoreStatus = undoneTask.getNewStatus().equals(OCCUPIED.label())
        ? DIRTY.label()                    // a room that held a guest is re-cleaned
        : undoneTask.getPreviousStatus();  // normal case: straight revert

The room re-enters the cleaning pipeline from the top, and the UI says so: “Room needs cleaning before the next check-in.”

If they ask

Questions worth an answer in your pocket

Why keep a stack when you already have the log?

Two access patterns. Undo needs the newest change for one room and needs it removed — that is LIFO, constant time on a stack. The log must keep every record forever, in order, for the activity report. Forcing one structure to do both would mean either deleting audit history or scanning the whole log on every undo.

What stops two modules fighting over the same room?

Guard 2. The undo compares the top of the stack against the room’s live status; if the front desk has moved the room since, they no longer match and the undo is refused. The DAO methods that mutate state are also synchronized.

Where is the Java Collections Framework?

Nowhere in the runtime storage. Data lives in a hand-written LinkedStack and plain arrays, and ordering is a hand-written selection sort. The only java.util types involved are Comparator and Predicate — functional interfaces, not collections — plus Arrays.copyOf as an array helper and Gson for file I/O.

What happens to task IDs after a restart?

load() calls restoreCounter(nextTaskId) from the file, and every restored task also runs through updateTaskIdCounter(), which takes the maximum. The counter only moves forward, so IDs never repeat.

What if the JSON references a room that does not exist?

load() throws IllegalStateException naming the task and the missing room number. It fails loudly at startup rather than silently dropping history.

Why save the task before updating the room?

So an audit record can never be missing for a change that happened. If save() fails, the room is left untouched and the UI reports SAVE_FAILED. Both writes reach disk immediately, through a temp file and an atomic move.

Does undo history survive a restart?

Yes. Each task is persisted with an active flag. On load, active tasks are pushed back onto their room’s stack and undone ones go into the log only — so the “Undo?” column and the Active / Undone markers look exactly as they did before you closed the app.

Are there limits?

Yes, and they are explicit constants in TaskStore: MAX_ROOMS = 50 undo stacks and MAX_TASKS = 500 log entries. Past that, save() returns false and the update is rejected rather than silently overwriting.
